## 1. Initial repository review

The repository was inspected without changes. The review covered project
structure, Git status, routes, PostgreSQL schema and startup migrations, HTML
templates, authentication and authorization, approval rounds, document versions
and S3 access.

The implementation was found to be a compact Go/Gin monolith using:

- PostgreSQL through `pgx`;
- server-rendered Go templates with a small HTMX interaction;
- private S3-compatible storage;
- database-backed sessions and role checks;
- startup migrations embedded in `main.go`.

The review confirmed login/logout, forced password changes for ordinary newly
created users, soft user deletion, immutable document versions, approval rounds
tied to exact versions and authenticated downloads through the application.

The main gaps identified at that point were:

- incomplete `go.mod`/`go.sum` metadata and formatting differences;
- no automated tests;
- no CSRF protection;
- no login attempt limiting;
- upload validation based mainly on filename extension;
- no dedicated audit journal;
- only the latest approval round displayed;
- possible orphaned S3 objects after a failed database transaction;
- an initial administrator was not forced to change the environment-provided
  password;
- stale text and an unused template remained in the UI.

Direct tests initially failed because the sandbox Go cache was read-only and the
module required `go mod tidy`. Tests in a temporary copy passed after tidying.

## 3. Security baseline

CSRF protection was added to every state-changing form and route, including
login, logout, password changes, user administration, document uploads and
approval actions.

Authenticated CSRF tokens are derived from the session. The login page uses a
separate short-lived CSRF cookie. Invalid or missing tokens return HTTP 403.

An in-memory login limiter was added. Five failed attempts for an email/network
address pair block further attempts for fifteen minutes. A successful login
clears the counter. The limitation is intentionally local to one application
instance and resets on restart.

Tests cover valid/invalid CSRF tokens, login CSRF, rate limiting, permitted and
forbidden roles, secure cookie behavior and the presence of CSRF fields in all
POST forms.

Relevant commit: `cb55c0b` (`Add CSRF защиту`).

## 7. Audit journal

An administrator-only audit journal was added at `/admin/audit`. It records:

- login and logout;
- user creation, password reset, password change and deactivation;
- document creation and version upload;
- approval start, participant response, completion and cancellation.

Events store snapshots of actor identity and role, target labels and exact
document versions where applicable. Passwords, session tokens, S3 keys and
approval comment bodies are not copied into audit records.

Audit writes are part of the same database transactions as their business
actions. PostgreSQL prevents ordinary updates and deletes of audit events. The
administrator page supports filters by event, actor, document and date.

Relevant commit: `a3fe7bc` (`Add audit /admin/audit`).

## 8. Upload content validation

Upload validation was strengthened without adding a production dependency.

- PDF validation checks the header, supported version and final EOF marker.
- Legacy DOC validation checks the OLE signature and Word document stream name.
- DOCX validation checks ZIP integrity, required package entries, Word XML
  metadata, path safety, duplicate names, decompression limits and macro content.
- Confirmed formats receive canonical MIME types rather than trusting the browser.

Tests include valid samples, renamed/plain-text files, truncated PDFs, malformed
DOCX archives, missing metadata and macro-enabled content.

Relevant commit: `dc7e660` (`усиленная проверка загрузок`).

## 9. Agreed target business process

The owner and assistant designed the target workflow one decision at a time. The
complete normative description is in `README.md`, section
`Целевая бизнес-логика`, and should be treated as the source of truth rather than
duplicated here.

The major decisions reached during the discussion were:

- The approval unit is a question containing a bundle of independently versioned
  files, not a single document.
- Questions cover budgets, internal documents/LNA, transactions/contracts, KPI,
  organizational matters and other Board-related matters.
- Contract questions require counterparty, amount, currency, the contract and a
  summary of principal terms. LNA questions require the draft LNA.
- Official files and review attachments support DOC, DOCX, XLS, XLSX and PDF,
  with a 25 MB per-file limit.
- The four mandatory internal services are Legal, Finance, Construction and
  Security directorates.
- Each service may have multiple representatives, but exactly one official visa
  is required per service and current file version. Different representatives
  may visa different files.
- Internal decisions are: approved, approved with comments, rejected, and no
  comments without review.
- All four services see the complete bundle and each other's responses. Internal
  review runs in parallel and must receive every required visa before proceeding.
- Rejected files must be revised. Rejecting services are always reassigned;
  the secretary may choose additional services. Positive visas can be explicitly
  carried forward from earlier versions.
- Representatives may upload initial files and revisions. Non-secretary uploads
  require secretary confirmation; rejected uploads remain in history.
- A pending revision pauses review only for its file.
- Internal and Committee decisions can be withdrawn within 24 hours while the
  round remains open; all history is retained.
- The secretary manually transfers a successfully reviewed question to the
  Committee and sets a separate voting deadline.
- Every active Committee member receives every question. Committee members see
  internal visas and live votes from other Committee members.
- Committee choices are for, for with comments, against and abstain. Comments are
  mandatory for all except an unqualified vote for.
- Quorum means more than half of the frozen Committee roster has responded.
  Abstention counts for quorum but not as support. Adoption requires more than
  half of all respondents to vote for or for with comments. The chair has no
  casting vote.
- Voting closes automatically when everyone responds. At the deadline, the
  secretary may close with quorum, extend with a mandatory reason, or close for
  lack of quorum.
- A positive result freezes the exact question bundle. A failed vote can be
  followed by another round in the same question.
- Protocols combine multiple independently voted questions, use manual agenda
  order and receive unique yearly numbers such as `1/2026`.
- Protocols are generated as HTML and downloadable Word documents. They are a
  convenience for the secretary, not the legal archive. Signed paper records are
  stored elsewhere.
- Email delivery and reminder details are intentionally deferred.
