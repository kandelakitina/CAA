# Развёртывание Neva Approvals на офисном сервере

Подготовлено 08.09.2026 по текущему коду репозитория. Для владельца и системного администратора. Команды ниже предназначены для Linux на будущем сервере; они не выполнялись в рабочем окружении и не являются проверенным установочным скриптом. Приложение и облачная инфраструктура при подготовке инструкции не изменялись.

Исходное условие: система ещё не эксплуатировалась. На выбранной площадке создаются новая пустая БД и новый приватный бакет; переноса данных с другой площадки нет.

## 1. Что предлагается

Разместить приложение, PostgreSQL и S3-совместимое хранилище в офисе. Пользователи открывают сайт по HTTPS из разрешённой корпоративной сети; из дома — после подключения к корпоративному VPN с MFA. MFA — второй фактор входа, например аппаратный ключ или приложение-аутентификатор. Доступ к самому приложению по-прежнему требует личного логина и пароля.

Один компьютер подходит для пилота и небольшой системы, если компания принимает простой при его отказе. Для единственного экземпляра договоров, бюджетов и истории согласований обязательны отдельные проверенные резервные копии и ответственный администратор. Само размещение в офисе не делает систему безопаснее облака.

| Компонент | Назначение | Размещение |
|---|---|---|
| Caddy | HTTPS и передача запросов приложению | Офисный сервер, 443/TCP |
| Go-приложение | Пользователи, согласования, скачивание | Тот же сервер, 8080; закрыт сетевым экраном |
| PostgreSQL | Реквизиты, версии, визы, голоса, аудит | Тот же сервер, только loopback |
| S3 | Содержимое всех файлов | Локальный сервис либо отдельное офисное хранилище |
| VPN | Удалённый доступ | Предпочтительно отдельный поддерживаемый шлюз |
| Резервные копии | Восстановление после аварии/атаки | Другой носитель и другая физическая площадка |

Для полностью офисного размещения и приложение, и PostgreSQL, и S3 создаются в локальном контуре. Если выбрать облачное S3 при офисном приложении, получится гибрид: файлы будут храниться в облаке, а доступ к ним будет зависеть от интернета.

## 2. Что приобрести и согласовать

Начальная инженерная оценка для небольшой группы, а не результат нагрузочного теста: выделенный компьютер с 4 современными ядрами, 16 ГБ RAM и двумя SSD в зеркале; ECC-память желательна при поддержке платформой. Ёмкость выбирать после подсчёта текущего объёма, роста всех версий и вложений, запаса минимум 30% свободного места. Два SSD по 1 ТБ — пример, а не обязательная спецификация. Зеркало дисков не заменяет резервную копию.

Нужны ИБП с автоматическим корректным завершением работы, проводная сеть, закрываемое проветриваемое помещение, отдельный носитель/сервер резервного копирования и способ восстановиться на другом компьютере. Не использовать сервер для почты, браузера и повседневной работы сотрудника. NAS в том же офисе не защищает от пожара и кражи всей техники.

До запуска назначить основного администратора и заместителя; определить, сколько данных допустимо потерять (RPO) и сколько ждать восстановления (RTO). Пример начальной цели: RPO 24 часа, RTO один рабочий день. Если потеря сегодняшних голосов неприемлема, нужны более частые согласованные копии БД и S3, а затем тест восстановления. Для RPO порядка минут потребуется отдельный проект WAL-архивирования PostgreSQL и согласованной защиты файлов.

## 3. Подготовка ОС и сети

Использовать поддерживаемую Ubuntu Server LTS, например 24.04 LTS с актуальными исправлениями. Установить PostgreSQL, Caddy и Go из поддерживаемых источников. Версия Go должна понимать `go.mod` (в нём `go 1.23.0`), но старую ветку 1.23 не следует выбирать только из-за этой строки: собирать актуальным поддерживаемым Go после тестов. Записать версии пакетов и контрольные суммы скачанных бинарников в паспорт сервера.

Сроки поддержки сверять перед установкой: [Ubuntu release cycle](https://ubuntu.com/about/release-cycle), [политика поддержки Go](https://go.dev/doc/devel/release).

Раздел с данными, swap и временные файлы должны находиться на зашифрованном диске. Для Linux подойдёт LUKS. Отдельно продумать разблокировку после перезагрузки: автоматическое включение питания не гарантирует запуск зашифрованного сервера. Ключ восстановления хранить отдельно от устройства в корпоративном хранилище секретов.

Выделить серверный VLAN/подсеть. Пример адресов: сервер `10.20.30.10`, сотрудники `10.20.10.0/24`, VPN `10.20.40.0/24`, администраторы `10.20.50.0/24`. Заменить их на реальные согласованные значения.

| Соединение | Правило |
|---|---|
| Сотрудники и VPN → сервер | Разрешить 443/TCP |
| Администраторы → сервер | Разрешить 22/TCP, SSH по ключам |
| Любая внешняя машина → 8080, 5432, S3 и его консоль | Запретить; для отдельного S3 разрешить только сервер приложения/backup |
| Интернет → офисное приложение | Не пробрасывать 443 и 8080 на роутере |
| Интернет → VPN-шлюз | Только порты выбранного VPN |
| Гостевой Wi-Fi → серверная сеть | Запретить |

Применить правила и для IPv4, и для IPv6. Настраивая firewall удалённо, сначала разрешить административное подключение и иметь локальную консоль. SSH root-login и вход по паролю отключать после проверки входа по ключу. Обычный WireGuard сам по себе не даёт пользовательскую MFA: её должен обеспечивать выбранный шлюз/система доступа.

Указать во внутреннем DNS имя, например `edo.corp.example.com`, на адрес сервера. Здесь `example.com` — заполнитель; использовать поддомен домена компании. VPN должен выдавать клиентам правильные маршруты и DNS. При CGNAT удалённый доступ требует решения с провайдером или согласованного VPN-транспорта; проброс порта сам по себе не поможет.

## 4. PostgreSQL

Для новой установки выбрать поддерживаемую версию PostgreSQL и проверить приложение на ней в тестовом контуре. Привязки к версии какой-либо ранее созданной БД нет. Зафиксировать выбранную версию; дальнейшие обновления основной версии проводить отдельным этапом.

На новом сервере создать отдельного владельца БД без суперправ. В интерактивном `sudo -u postgres psql`:

```sql
CREATE ROLE neva LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password neva
CREATE DATABASE neva_approvals OWNER neva;
```

`\password` позволяет задать пароль без записи его в SQL-команду. Использовать длинный случайный пароль. В `postgresql.conf` установить `listen_addresses = '127.0.0.1'`, `password_encryption = 'scram-sha-256'`. В `pg_hba.conf` разрешить:

```text
host neva_approvals neva 127.0.0.1/32 scram-sha-256
```

Проверить порядок и остальные правила, исключить внешние разрешения и `trust`. Перезапустить PostgreSQL и проверить реальные слушающие адреса. Приложению сейчас нужны права создавать и изменять таблицы: миграции выполняются автоматически при старте. Поэтому роль является владельцем своей БД; отдельную роль для миграций можно внедрить позднее изменением приложения.

## 5. Локальное S3

Просто указать папку вместо `S3_ENDPOINT` нельзя: приложение использует S3 API с path-style адресацией. Для промышленной эксплуатации выбрать поддерживаемое локальное S3-решение с документированной процедурой восстановления. Проверить `HeadBucket`, `PutObject`, `GetObject`, `DeleteObject`, SigV4, работу метаданных и всех используемых `VersionId` именно текущим AWS SDK приложения.

Ниже — конкретный вариант **пилота с новой пустой БД** на Garage. Его односерверный quick start не рекомендован разработчиками для production из-за отсутствия избыточности. Для корпоративной эксплуатации потребуется либо поддерживаемое промышленное хранилище, либо отдельное проектирование отказоустойчивого кластера. Три процесса на одном компьютере не устраняют отказ самого компьютера. [Garage Quick Start](https://garagehq.deuxfleurs.fr/documentation/quick-start/).

Установить проверенный бинарник Garage в `/usr/local/bin/garage`; пример использует интерфейс версии 2.3.0, перед установкой проверить исправления и актуальность выбранного релиза. Создать пользователя `garage` без shell и каталоги `/var/lib/garage/meta`, `/var/lib/garage/data`, принадлежащие ему. Файл `/etc/garage.toml` сделать `root:garage`, права `0640`:

```toml
metadata_dir = "/var/lib/garage/meta"
data_dir = "/var/lib/garage/data"
db_engine = "sqlite"
replication_factor = 1
data_fsync = true
rpc_bind_addr = "127.0.0.1:3901"
rpc_public_addr = "127.0.0.1:3901"
rpc_secret = "REPLACE_WITH_RANDOM_64_HEX_CHARACTERS"

[s3_api]
s3_region = "garage"
api_bind_addr = "127.0.0.1:3900"
```

Пути постоянные; `/tmp` для хранения документов недопустим. Публичный website endpoint не включать. Параметры сверены с [конфигурацией Garage](https://garagehq.deuxfleurs.fr/documentation/reference-manual/configuration/).

Создать `/etc/garage-bootstrap.env` с правами `0600`, владелец root. Внести новые случайные значения в `GARAGE_DEFAULT_ACCESS_KEY` (формат `GK` и 32 шестнадцатеричных символа), `GARAGE_DEFAULT_SECRET_KEY` (64 шестнадцатеричных символа), `GARAGE_DEFAULT_BUCKET=neva-documents`. Секреты генерировать и сохранять локально, не в истории команд и переписке.

`/etc/systemd/system/garage.service`:

```ini
[Unit]
Description=Local S3 for Neva pilot
After=network.target

[Service]
User=garage
Group=garage
EnvironmentFile=/etc/garage-bootstrap.env
ExecStart=/usr/local/bin/garage -c /etc/garage.toml server --single-node --default-bucket
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/var/lib/garage
UMask=0077

[Install]
WantedBy=multi-user.target
```

После `systemctl daemon-reload` и `systemctl enable --now garage` проверить `garage -c /etc/garage.toml status` от пользователя с доступом к конфигурации и данным. После первоначального создания сохранить ключи в защищённом хранилище; можно убрать bootstrap-параметры из unit и env, оставив `server`, после проверки сохранности layout и ключей. Общая организация службы соответствует [руководству systemd для Garage](https://garagehq.deuxfleurs.fr/documentation/cookbook/systemd/).

У Garage нет bucket versioning и стандартных S3 IAM policies; его права выдаются ключу на бакет. Не приписывать ему Object Lock. История версий приложения и версионирование самого S3 — разные вещи. При запуске с пустой БД старых S3-идентификаторов нет. Нужно проверить создание и скачивание нескольких версий через приложение; отсутствие bucket versioning по-прежнему ограничивает защиту от удаления на уровне хранилища. [Совместимость Garage](https://garagehq.deuxfleurs.fr/documentation/reference-manual/s3-compatibility/).

## 6. Сборка и конфигурация приложения

Собирать утверждённую ревизию в отдельной рабочей папке под обычным пользователем; секреты production туда не помещать:

```bash
go mod download
go test ./...
go vet ./...
go build -trimpath -o app .
```

Проверить уязвимости Go и зависимостей поддерживаемым `govulncheck`. Интеграционные тесты запускать только на отдельной тестовой БД и бакете; обычный успешный `go test` не доказывает работу с реальными PostgreSQL/S3.

Создать системного пользователя `neva` без интерактивного входа. Разместить бинарник `app`, каталоги `templates/` и `static/` в `/opt/neva/releases/RELEASE_ID/`, установить ссылку `/opt/neva/current` на релиз. Файлы принадлежат root и доступны neva для чтения/исполнения, без права изменять код. Каталоги нужны рядом с бинарником: шаблоны не встроены внутрь него.

Создать `/etc/neva/app.env`, root:root, `0600`; каталог `/etc/neva` — `0700`. Это файл для systemd, приложение само `.env` не читает. Значения `REPLACE_...` обязательно заменить:

```dotenv
PORT=8080
GIN_MODE=release
PGHOST=127.0.0.1
PGPORT=5432
PGDATABASE=neva_approvals
PGUSER=neva
PGPASSWORD=REPLACE_WITH_RANDOM_DB_PASSWORD
PGSSLMODE=disable
SESSION_SECRET=REPLACE_WITH_RANDOM_SECRET_AT_LEAST_32_CHARACTERS
INITIAL_ADMIN_EMAIL=admin@example.com
INITIAL_ADMIN_PASSWORD=REPLACE_WITH_UNIQUE_LONG_PASSWORD
INITIAL_ADMIN_NAME="Администратор"
S3_ENDPOINT=http://127.0.0.1:3900
S3_REGION=garage
S3_BUCKET=neva-documents
S3_ACCESS_KEY_ID=REPLACE_WITH_BUCKET_KEY
S3_SECRET_ACCESS_KEY=REPLACE_WITH_BUCKET_SECRET
```

`disable` и HTTP допустимы здесь только для loopback на одном защищённом сервере. Если PostgreSQL или S3 на другой машине, использовать TLS с проверкой сертификата, для PostgreSQL — `verify-full` и доверенный CA; частная сеть не заменяет шифрование. Секрет сессий — случайные минимум 32 символа, лучше 32 случайных байта в hex. Начальный пароль — уникальный длинный; минимум кода 8 символов недостаточен как корпоративная рекомендация.

`/etc/systemd/system/neva.service`:

```ini
[Unit]
Description=Neva Approvals
After=network-online.target postgresql.service garage.service
Wants=network-online.target

[Service]
User=neva
Group=neva
WorkingDirectory=/opt/neva/current
EnvironmentFile=/etc/neva/app.env
ExecStart=/opt/neva/current/app
Restart=on-failure
RestartSec=10
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
UMask=0077

[Install]
WantedBy=multi-user.target
```

Сначала поднять БД и S3, затем выполнить `systemctl daemon-reload` и `systemctl enable --now neva`. Приложение слушает `0.0.0.0:8080`, поэтому внешний доступ к 8080 обязательно закрыть firewall. Проверить `curl --fail http://127.0.0.1:8080/health`. Этот endpoint проверяет БД, но **не проверяет S3**.

## 7. HTTPS

В `/etc/caddy/Caddyfile` для закрытого контура:

```caddyfile
edo.corp.example.com {
    tls internal
    request_body {
        max_size 270MB
    }
    header {
        X-Content-Type-Options nosniff
        Referrer-Policy no-referrer
        X-Frame-Options DENY
        Cache-Control "private, no-store"
    }
    reverse_proxy 127.0.0.1:8080
}
```

Лимит рассчитан с запасом на форму с десятью вложениями по 25 МиБ и служебные поля; лимиты самого приложения сохраняются. Проверить синтаксис установленной версией: `caddy validate --config /etc/caddy/Caddyfile`, затем перезагрузить службу. [Caddy request_body](https://caddyserver.com/docs/caddyfile/directives/request_body).

При `tls internal` установить корневой сертификат CA Caddy в доверенные хранилища управляемых компьютеров и браузеров. Передавать только публичный сертификат, не закрытый ключ CA. Не обучать сотрудников обходить предупреждения браузера. Альтернатива — корпоративный CA или публичный сертификат через DNS-01; для DNS-01 нужен соответствующий модуль Caddy и ограниченный DNS API token. Публиковать сайт в интернете ради сертификата не требуется. [HTTPS Caddy](https://caddyserver.com/docs/automatic-https), [reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

Cookie приложения уже имеют Secure и HttpOnly; вход по обычному HTTP не является корректной производственной схемой. После доверенного HTTPS проверить вход и смену пароля. У начального администратора смену организовать явно, не полагаться на автоматическое требование: начальная запись создаётся отдельным путём. Удалить `INITIAL_ADMIN_PASSWORD` из env после создания и перезапустить службу; при существующих пользователях он не нужен.

## 8. Проверка до допуска сотрудников

- Перезагрузить сервер: службы стартуют, диски разблокируются по согласованной процедуре, данные сохраняются.
- С разрешённого компьютера открыть сайт без ошибок сертификата; из гостевой сети проверить отказ. Снаружи убедиться, что 8080, 5432 и S3 недоступны, включая IPv6.
- Создать тестовые личные учётные записи. Проверить разрешённый и запрещённый доступ: секретарь создаёт вопрос, наблюдатель не может выполнить то же POST-действие, пользователь без доступа не скачивает файл по прямой ссылке.
- Пройти внутреннее согласование, голосование Комитета, новую версию и скачивание предыдущей; проверить вложения, протокол и аудит.
- Проверить допустимые форматы и размеры, десять вложений, отказ при превышении лимита, отключение пользователя и завершение его сессий.
- Проверить `/health`, затем `/storage/check` после входа и реальную загрузку/скачивание тестового файла. HeadBucket сам по себе не подтверждает права записи.
- Выполнить восстановление резервной копии на отдельном стенде и сравнить файлы. Проверить уведомления об отказе служб, S3 и резервного копирования.

До успешного восстановления использовать только тестовые документы. Полный сброс проверять исключительно на одноразовом стенде.

## 9. Первый запуск с нуля

Порядок одинаков по смыслу для офисного сервера и Timeweb; различаются способы создания служб и настройки сети.

1. Выбрать одну производственную площадку. Создать новую пустую PostgreSQL БД и отдельный приватный S3-бакет. Для тестов использовать другую БД и другой бакет с отдельными ключами.
2. Зафиксировать проверенный Git commit и версии компонентов. Настроить сетевой доступ, HTTPS и новые случайные секреты; в Timeweb передать настройки через переменные окружения App Platform, в офисе — через защищённый файл systemd из раздела 6.
3. Указать параметры именно выбранной площадки. Для облачного S3 взять endpoint, region и bucket из настроек созданного хранилища; значения локального Garage в облачную конфигурацию не копировать. PostgreSQL подключать по разрешённому адресу, с TLS и проверкой сертификата при сетевом соединении.
4. Задать `INITIAL_ADMIN_EMAIL`, `INITIAL_ADMIN_PASSWORD` и при необходимости `INITIAL_ADMIN_NAME`. Запустить один экземпляр приложения: он создаст таблицы и начального администратора. Автоматические «миграции» здесь означают создание/обновление схемы таблиц, а не перенос данных с Timeweb.
5. Проверить `/health`, вход по HTTPS, смену начального пароля и доступ к S3. Удалить начальный пароль из конфигурации после создания администратора. Создать личные учётные записи и назначить роли.
6. В отдельном тестовом контуре пройти сценарии раздела 8 и восстановление backup. Производственный контур проверить без реальных корпоративных документов; если создаются тестовые записи, заранее определить порядок их учёта, не использовать полный сброс как обычный шаг запуска.
7. Включить резервное копирование, мониторинг и уведомления до начала эксплуатации. Зафиксировать ответственных, дату допуска и результаты проверок. После этого разрешить загрузку реальных документов.

Для нового запуска не нужны выгрузка старой БД, копирование бакета, сопоставление `VersionId`, отзыв перенесённых сессий и переключение со старой системы. Новая пустая инфраструктура создаётся отдельно; эта инструкция не предполагает удаление уже существующих облачных ресурсов.

## 10. Резервное копирование и эксплуатация

Минимум: рабочие данные, отдельная резервная копия и ещё одна зашифрованная копия вне офиса; одна копия недоступна для изменения/удаления рабочему серверу. При запрете облачного хранения использовать второй защищённый офис либо ротацию отключаемых шифрованных носителей. Хранить ключи восстановления отдельно. [CISA: защита резервных копий](https://www.cisa.gov/stopransomware/ransomware-guide).

Для небольшой системы самый понятный согласованный backup: окно обслуживания → остановить приложение и иных писателей → создать dump БД → сохранить все файлы S3 с манифестом → убедиться в успешном завершении → запустить приложение. Для пилотного Garage можно после остановки приложения остановить Garage и копировать его данные **вместе с метаданными и конфигурацией**, затем поднять службы. Горячую копию каталога работающей БД или Garage нельзя считать корректным backup без поддерживаемого механизма snapshot. План должен предусматривать возврат сервиса и уведомление даже при ошибке копирования.

Пример политики для согласования: ежедневные копии 30 дней, ежемесячные 12 месяцев; архив юридически значимых материалов — по корпоративной политике хранения. Сроки backup не заменяют сроки хранения документов. В комплект восстановления входят БД, S3, манифест, релиз, конфигурация и защищённые ключи; нельзя хранить всё только на том же диске. Архивы с секретами должны иметь ещё более узкий доступ.

Ежедневно: автоматическая проверка успешности backup, места, ошибок БД/S3 и доступности сайта с уведомлением ответственному. Еженедельно: проверка скачивания и контрольных сумм выборки, дисков/ИБП. Ежемесячно: восстановление на изолированном стенде, проверка доступа пользователей и обновлений. После крупных изменений — повторная полная проверка восстановления. Уведомлять о заполнении диска заранее, например при 70% и 85%.

Обновлять через новый каталог релиза: backup → тест на копии → окно обслуживания → остановка приложения → переключение ссылки → запуск → проверки. Миграции выполняются при запуске, общий стартовый timeout в коде 15 секунд; на большой БД обновление может потребовать отдельной доработки этого механизма. Откат бинарника после миграции не гарантирует совместимость схемы: нужен заранее проверенный план восстановления БД и файлов.

При атаке изолировать сервер от сети, сохранить доступные журналы и доказательства, отозвать сессии и ключи с чистого устройства; восстанавливать на чистой системе после устранения причины. Простое восстановление поверх заражённой ОС не решает проблему.

## 11. Критерий готовности

Систему можно передавать в эксплуатацию после назначения ответственных, проверки сетевой изоляции и HTTPS, закрытия критичных замечаний из `SECURITY_DEPLOYMENT_COMPARISON.md`, успешного сквозного согласования и доказанного восстановления на другой машине. Для промышленного варианта выбор и приёмка локального S3 остаются обязательным инженерным этапом; пилотный Garage на одном узле не объявляется отказоустойчивым решением.
